<h2>TL;DR</h2><ul><li><p>llm-wiki 和 context-infrastructure 都是信息复利系统，前者从知识中沉淀出AI可复用的知识结构，得到一个知识索引wiki；后者从生活记录中沉淀出个人特质，得到个人的行为模式和行动准则。</p></li><li><p>llm-wiki 通过将外部知识组织成wiki，让AI在wiki上进行问答，将知识结构沉淀为复利，同时将用户维护知识库的脑力节省出来，沉淀成脑力复利。</p></li><li><p>context-infrastructure 从大量的、随时间积累的生活记录中蒸馏出一个人的行为模式和准则，AI可以利用这些准则进行工作，从而形成了一种复利。</p></li><li><p>信息复利设计的关键是把未来会反复用到的信号，提前提炼成默认工作面。</p></li></ul><h2>1. 绪论</h2><p>我最近发现，Andrej Karpathy的llm-wiki 和鸭哥的context-infrastructure 似乎有共同之处。我分析了这两个系统的设计，得到了一些关于如何让数据产生复利的learnings。</p><p>llm-wiki 是 Andrej Karpathy 提出的一个模式（见 <a href="https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f">karpathy/llm-wiki gist</a>）。它主张把原始材料和最终问答之间，插入一个由 LLM 持续维护的 wiki 中间层。新材料进入后，不只是被索引，而是被读入、综合、交叉链接，并逐步编译成可以长期复用的知识结构。</p><p>context-infrastructure 则是鸭哥公开的一套个人 agent 工作系统（背景文章见 <a href="https://yage.ai/context-infrastructure.html">为什么 AI 只会说正确的废话，以及怎么把它逼出舒适区</a>，公开仓库见 <a href="https://github.com/grapeot/context-infrastructure">grapeot/context-infrastructure</a>）。它把规则、记忆、skills、周期性观察与反思任务放进同一个 workspace，目标不是单纯让 agent 知道更多，而是让 agent 在长期协作中逐步继承一个人的偏好、风格、边界和判断方式。</p><p>两者的共同母题是<strong>让数据中有价值的信息可以被沉淀成复利，可被反复利用</strong>。它们都在反对一种默认工作方式：每次提问都重新从原始材料出发，让模型临场检索、临场拼接、临场组织，问题结束后除了当前回答之外几乎不留下任何可持续增益。它们都认为，这种用法虽然方便，却无法积累理解。真正有价值的，不是让模型一次次重新理解，而是把那些未来还会反复有用的信息先提取出来，沉淀成一个会复利的中间层。</p><p>从这个角度看，llm-wiki 和 context-infrastructure 可以被归类为一种“信息复利系统”。前者处理客观知识，后者处理生活记录。它们都在做提炼，但提炼对象不同，噪音结构不同，优化目标不同，因此架构设计也不同。</p><h2>2. llm-wiki的设计</h2><p>先看 llm-wiki。它面对的原始材料通常是论文、文章、报告、书籍、团队文档这一类外部知识。这些材料通常已经是高信号密度的表达。作者知道自己在讲什么，主题边界相对清晰，材料本身已经经过了一轮人类整理。所以 llm-wiki 面对的核心问题，并不是怎样从噪音里找出极少数信号，而是怎样把大量已经有价值、但分散在不同地方的知识持续编译成一个可以导航、可以维护、可以复用的中间层。</p><p>llm-wiki 的设计依赖了对传统RAG的一个关键洞察：如果把知识搜索-聚合放在问答的过程中，则系统实际上没有真正积累理解，只是在反复支付理解成本。相反，如果我们可以把知识搜索-聚合的过程提前到问答发生前，我们不仅可以节省一次问答的搜索成本，聚合的产物还可以产生知识复利。使用传统RAG+LLM回答一个复杂问题时，LLM也许能答出来，但下一次相近的问题又要重新走一遍同样的路。随着材料增多，这种成本只会越来越高。提前完成结构整理、交叉链接、摘要更新、冲突记录这些维护工作，让之后的查询站在一个已经被编译过的知识中间层之上，LLM每次搜索的成本会变低，节省出来的token可以用于更高质量的回答。这些高质量的回答再沉淀回中间层，便形成了一个飞轮。</p><p>llm-wiki 产生的另一个复利是让人的脑力投入真正高价值的工作。它让 LLM 接管知识维护的重活，让用户把注意力留给提问、分析和方向判断。用户节省出来的脑力也可以进一步提高他自己的工作质量。</p><p>由此， llm-wiki 的设计是更简洁的 raw data-wiki 两层架构，并且工作流更依赖开放式的 agentic 探索。由于数据高度结构化、信息密度高，LLM直接进行提炼总结便可以得到很好的效果。为了产生上述的知识复利和脑力复利， llm-wiki 可以根据用户提问，从原始数据中重新查找信息，改写wiki页面，也可以把高价值的问答沉淀回wiki里。它的wiki页面保留的是结构化入口，agent 依据提问从这里出发展开探索，有时回到原始数据，有时跨页面综合，有时把新的问题和回答写回wiki里。中间层是为了让探索更有抓手，而不是为了结束探索。</p><h2>3. context-infrastructure 的设计</h2><p>如果说 llm-wiki 处理的是高信号但分散的知识，那么 context-infrastructure 处理的则是另一种困难数据：高噪音但可能极有价值的个人痕迹。这里的输入不再主要是论文、文章、书籍，而更像聊天记录、邮件、会议纪要、随手记录、工作区痕迹和日常行为线索。它们的共同特点是时间连续、信息密度不稳定、表达经常不完整，而且包含大量对未来毫无意义的噪音。</p><p>context-infrastructure 依赖一个核心洞察：大量表面上杂乱的生活痕迹背后，存在较少但稳定的潜在偏好与判断结构。这让人联想到生成式AI领域的“高维数据背后存在低维潜在结构”这一个发现。真正有价值的，不是某一句话的字面内容，而是这些生活碎片长期累积后隐含出来的偏好、边界、风格、判断方式和非共识倾向。</p><p>这就解释了为什么 context-infrastructure 不能长成一个薄薄的 “raw data -&gt; wiki” 结构。它面对的主要问题不是知识散落，而是信号稀薄。它需要回答的是另一类问题：在大量高噪音个人痕迹里，怎样渐进地识别并保留那些少量但稳定的个人信号，并把它们转化成 agent 可继承的行为基础设施。</p><p>context-infrastructure 采用了一套多层的信息提炼机制。每当有新的原始数据到来时，它从中提炼出对个人行为的观察（observations）。当observations积累得足够多时，它从中提炼出行为模式（patterns）。进一步地，它从积累的patterns中提炼出个人的行为准则（axioms）。raw data -&gt; observation -&gt; pattern -&gt; axiom 形成了一套必要的多层去噪机制。因为原始记录噪音过大，信号太过于稀薄，所以需要一个多层的提炼机制来筛选信号。和 llm-wiki 的agentic探索不同，context-infrastructure 的工作流更接近简单循环的闭环结构。由于原始数据价值很低，所以它追求的是让日常任务越来越少依赖原始数据，真正有用的个体信号应当已经在上层结构里被提炼出来。</p><p>并且，可以注意到，个人的生活数据是按时间慢慢积累的，为了积累足够大量的数据来提取patterns和axioms，这套系统的工作流需要定时地、循环地运行。因此，context-infrastructure 需要使用cron定时任务来定期运行总结、提炼的机制。它有点像一种在线学习过程。新的记录持续到来，新的 observation 会改变之后的判断，信号会不断被晋升，噪音则停留在低层甚至被遗忘。系统不是一次性成型的，而是在与人的长期互动中逐步收敛。</p><h2>4. 信息复利系统的设计洞察</h2><p>从 llm-wiki 和 context-infrastructure 往上抽象，可以得到一个更一般的洞察：</p><blockquote><p>信息复利设计的关键是把未来会反复用到的信号，提前提炼成默认工作面。</p></blockquote><p>这句话看起来简单，但它几乎重新定义了“memory system”该怎么设计。真正重要的，不是系统有没有保存足够多的原始数据，而是未来的工作，究竟站在哪一层上发生。如果未来任务仍然总是回到 raw data，重新检索、重新拼接、重新判断，那么系统只是有存储，没有复利。只有当被提炼过的中间层成为默认工作面，复利才会真正开始。</p><h3>4.1. 为什么“默认工作面”比“信息存储”更关键</h3><p>很多系统也会保存历史数据、做标签、做摘要、做索引，看上去已经比一次性问答更先进。但这些能力本身，还不足以构成信息复利。</p><p>原因很直接。存储只是把信息留下来，复利则要求未来工作能直接站在已经提炼过的结果上继续进行。如果系统只是把原始数据存得越来越多，而未来问题仍然必须重新回到原始材料里理解一遍，那么它本质上还是在反复支付同样的理解成本。</p><p>这就是为什么“默认工作面”这个概念更关键。</p><p>所谓默认工作面，指的是未来的大多数任务，首先接触、首先依赖、首先在上面继续推理和行动的那一层。它不一定是最底层，也不一定是最完整的一层，但它必须是最常用、最可调用、最能降低未来理解成本的一层。</p><p>从这个角度看，一个系统是否具有复利，不取决于它存了多少数据，而取决于它有没有把高价值信号提前搬到未来工作的起点上。</p><h3>4.2. 这条洞察如何解释 llm-wiki</h3><p>llm-wiki 的关键，不只是它有一个 wiki，而是它把 wiki 变成了默认工作面。</p><p>未来的大多数问题，不应该直接从原始论文、文章、报告重新开始，而应该先站在这个已经被持续维护的 wiki 上。这里的 wiki 不只是摘要集合，而是一个经过编译的知识中间层。交叉链接、主题结构、对比关系、已有综合，都是为了让后续工作不必每次再从 raw source 重新搭架子。</p><p>所以 llm-wiki 真正在做的，不是“保存知识”，而是“把知识编译成未来推理的默认起点”。</p><p>一旦这样看，它和传统 RAG 的差别就清楚了。传统 RAG 的主要工作面仍然更接近 raw data 的检索结果，而 llm-wiki 试图把工作面前移到一个已经整理过、结构化过、被持续维护的中间层。原始数据仍然存在，也仍然重要，但它们不再是默认起点，而更像验证层和补充层。</p><h3>4.3. 这条洞察如何解释 context-infrastructure</h3><p>context-infrastructure 的关键是它试图把某种已经提炼过的个人信号，变成 agent 的默认工作面。</p><p>对于这类系统来说，未来反复出现的任务，并不应该每次都重新从聊天记录、会议痕迹、工作区碎片里推测“这个人可能偏好什么、风格如何、边界在哪”。这些判断如果每次都要重新做，就说明系统没有复利。</p><p>所以它需要 observation、pattern、axiom这些层。它们的意义，不只是多做几层抽象，而是把那些会反复进入未来判断的个人信号提前提纯出来，让 agent 在大多数任务里先站在这些中间层上工作，而不是每次重新回到高噪音原始痕迹。</p><p>这里的默认工作面，已经不再是知识页面，而是个体化控制面。它回答的不是“世界上有什么”，而是“这个人通常怎样判断、怎样表达、怎样做取舍”。</p><h3>4.4. 从这里看，设计问题就变了</h3><p>一旦把信息复利系统理解成“把未来会反复用到的信号提前提炼成默认工作面”，系统设计的核心问题就不再是“怎么把信息都存下来”，而会变成下面这些更本质的问题。</p><p>第一，未来到底会反复用到什么信号。</p><p>不是所有信息都值得上升成默认工作面。值得上升的，通常是那些会反复参与未来推理、决策、表达、协作或执行的信息结构。它可以是知识、规则、模式、偏好、约束，也可以是某种判断模板。</p><p>第二，原始数据离这个信号到底有多远。</p><p>如果 raw data 本身已经高信号、主题清晰，那么提炼路径可以很短，默认工作面也可以比较薄。如果 raw data 高噪音、时序化、表达不完整，那么提炼路径就必须更长，否则默认工作面会被噪音污染。</p><p>第三，未来工作是否真的默认站在这层上发生。</p><p>这一步最容易被忽略。很多系统也会产生中间层，但未来工作并不真正使用它，或者只把它当阅读材料，而不是执行与判断的起点。这样一来，中间层虽然存在，却没有成为默认工作面，也就没有真正创造复利。</p><p>所以，信息复利设计真正要回答的，其实不是“该不该做中间层”，而是“哪一层能够成为未来工作的默认起点”。</p><h3>4.6. 一个新信息复利系统设计示例</h3><p>下面举一个和 llm-wiki、context-infrastructure 更不一样的例子。它来源于我自己读研过程中的痛点。</p><p>我研究生期间在做边缘计算与网络经济学的机制设计的相关工作。我们常常需要围绕一个系统模型和一个优化目标，从头构造机制、做大量理论推导、证明若干性质、再进入实验，最后才发现这个机制根本不值得继续。这里最浪费时间的地方，往往不是实验本身，而是研究者过早为一个还没被有效筛选过的猜想支付了高昂的理论成本。</p><p>如果用“默认工作面”这条洞察来看，这个场景里真正应该被提炼出来的，是更高层的研究判断信号，例如：哪类问题结构通常对应哪些机制模板，哪些机制在什么约束下大概率无效，哪些问题建模会让某类机制失去意义，哪些设计值得先做小规模仿真，哪些设计值得先投入理论推导。</p><p>只要这些信号还没有被稳定提炼出来，研究流程就会不断让理论推导充当第一道筛选器。每次新问题到来，研究者都几乎从原始的问题建模重新开始，重新设计机制、重新判断值不值得证明、重新为可能无效的方向支付时间。一旦这些研究判断被提炼成默认工作面，循环就会明显加快。新问题进入后，研究者首先调用的就不再是从零开始的推导能力，而是一个已经积累起来的经验层。这样一来，真正开始复利的就不是论文数量，而是“什么值得做”的研究判断本身。</p><h2>5. 结论</h2><p>从 llm-wiki 和 context-infrastructure 我们可以看到，不同的数据形态、不同的工作目标带来的不同信息复利系统的设计。由此，我们总结出一个洞察：信息复利系统设计最重要的是让系统拥有更好的默认工作面。所谓更好，指的不是更漂亮，而是更接近未来反复要用到的信号。</p><p>所以一个信息复利系统最重要的问题，始终是这一句：</p><blockquote><p>未来的高价值工作，到底应该默认站在哪一层上发生？</p></blockquote><p>如果答案仍然是 raw data，那系统再大也很难真正复利。</p><p>如果答案是一个被提前提炼出来、能被持续调用、更新、纠偏的中间层，那么复利就开始出现。</p><p>这也是为什么真正重要的设计动作，不是“收集更多信息”，而是“把未来会反复进入判断的信号提前搬到默认工作面上”。</p><p>从这个意义上说，信息复利系统设计，最终是在设计未来工作的起点。</p><p><strong>写在最后</strong>：感谢鸭哥开源 context-infrastructure。这篇文章经过AI润色，AI的语言表达风格的提示词直接使用了鸭哥 context-infrastructure 里的相关提示词。</p>
