<h2>🐶 gogo</h2><p>我在用 <a href="https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f">llm-wiki</a> 作为自己的第二大脑。但是一个痛点是，我需要同时打开 Obsidian 和 Codex，在两个工具之间来回切换。并且我只有一个屏幕，来回切换就超级麻烦。我又懒得给obsidian装插件，现有的插件又需要配置（如<a href="https://github.com/RAIT-09/obsidian-agent-client">acp</a>）。<br/>第二个痛点是，很难把 llm-wiki 这种模式安利给身边没有 IT 背景的朋友，因为他们需要下载安装 Coding Agent、配置运行环境和 LLM 模型。这个门槛足以让很多人望而却步。<br/>所以，我就自己做了（100% 纯 AI，零人工）一个 llm-wiki 的入口应用： <strong>gogo</strong>。把一个markdown浏览界面和一个<a href="https://pi.dev">Pi agent</a>（openclaw同款）直接打包在一起，可以做到开箱即用，无需配置（还是要配置自己的API key的）。<br/>现在，我把 gogo 作为自己日常使用 llm-wiki 的入口。虽然它远远没有到达完美水准，但是我觉得它基本能够满足我的需求。如果你也有类似的痛点，希望它也能帮到你。</p><p>项目已经开源在：<a href="https://github.com/Barytes/gogo">https://github.com/Barytes/gogo</a><br/>在Github Release 可以下载Windows x64 和 MacOS（Apple Silicon）版本的安装包。</p><div><figure><a href="https://substackcdn.com/image/fetch/$s_!fiCe!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F44a58521-e999-4e2c-9aed-d9d02ddfe37a_1470x956.gif"><div><picture><img alt="" loading="lazy" src="/blog/44a58521-e999-4e2c-9aed-d9d02ddfe37a_1470x956.gif"/></picture><div></div></div></a></figure></div><p></p><h2>设计原则和一些反思</h2><p>具体来说，设计gogo的时候考虑了下面的原则：</p><ul><li><p><strong>📦开箱即用</strong>：gogo 的目标是让用户尽量少做环境搭建，就能使用 llm-wiki。</p></li><li><p><strong>💁gogo 服务于本地 llm-wiki 知识库</strong>：为 llm-wiki 提供更好用的入口，而不是把知识和工作流反过来锁进应用本身。停止使用 gogo 也不会损失知识库内的任何内容。</p></li><li><p><strong>🤝统一 Wiki + Agent 工作面</strong>：gogo 把知识浏览和 AI 对话放进同一个工作面里，减少用户在多个工具之间来回切换的成本。</p></li><li><p><strong>🔍聚焦 llm-wiki 场景，而不是做通用知识管理器</strong>：gogo 优先把 llm-wiki 的工作流做到顺手，而不是为了更泛化的场景牺牲边界清晰度和使用体验。</p></li><li><p><strong>👑用户是知识库的第一拥有者</strong>：用户应该始终能看见、修改、迁移和替换自己的知识库结构、skills、schemas 和工作方式，而不是被迫接受封闭系统的默认安排。</p></li><li><p><strong>🤖不过度黑盒化 Agent 机制</strong>：gogo 不把 agent 包装成完全不可见的“魔法”，而是尽量让模型配置、slash 命令、诊断信息、上下文和权限边界都对用户透明。</p></li><li><p>🧠<strong>不做联网搜索</strong>：没有给 agent 加上联网搜索功能。一方面是，要求它完全忠于知识库内的内容回答，不要自我发挥，去网上搜索“共识‘内容——如果回答不好，说明应该寻找新材料加入知识库了。另一方面，我觉得人至少得自己去找新材料，自己了解知识库里存了什么内容。如果全部给 agent 代劳，那人就会倾向于放弃理解。</p></li></ul><p>回顾开发的过程，发现自己还是犯了不少错误</p><ul><li><p><strong>有必要做吗？</strong> 最开始是想给课题组做一个<a href="https://www.superlinear.academy/c/q-a?message_id=2099190673#message_2099012264">公共知识库</a>，但是产品的边界没有定义清楚，想要做一个大而全的产品，包揽wiki浏览--ai对话--知识共享三个功能。后来经过一番思考，觉得wiki浏览--ai对话和知识共享应该拆分成两个产品，就先把前两个功能做成了gogo。现在感觉，完全没有必要做这个产品，花费了很多精力，只是得到了一个副产品，没有真正去做自己想做的东西。</p></li><li><p><strong>只是一个套壳应用。</strong> 按照课代表<a href="https://www.superlinear.academy/c/ai-resources/ai-product">AI产品的六个层次</a>，gogo应该算是在L2-L4。虽然缝合了一个agent loop进去，但并不能称之为一个 Agentic Core/AI-native Product。Agent在其中还是主要用来做知识的检索，并且llm-wiki本身的ingest, write-back, lint等流程还是需要手动触发。其实可以做更多的优化，增加更多frictionless interaction、contextual intelligence、proactive intelligence的设计。</p></li></ul>
